The idea

The concept

Three patterns, all about where to put effort.

1. Fan out, verify adversarially, then filter. Code review is where the team first used a large fan-out: Claude searches for every possible bug in parallel, each candidate then gets an adversarial review from several perspectives to check whether it is real, and only survivors reach a human. They call it spending test-time compute to build confidence, and describe it as a MapReduce problem: once you fan out you have too much output, so you must filter back down for human consumption. The same shape works for performance issues and general research (their example is planning a trip). Claude writes the orchestration itself as code, so a plain loop guarantees every item gets the same treatment, which is why one speaker says it raises his trust.

Fan out, challenge, filter

2. Harness features are scaffolding for current model weaknesses, so they expire. The to-do list arrived when a model given five things would quietly stop after three. A year later it was barely needed. Another speaker spent a long time designing the ask-user-question tool, and now mostly gets questions through an HTML artifact with diagrams and mockups instead. The lesson they state is to stay unattached to what you build: it covers a failure mode the next model may not have, and then you check what the bigger tasks now require.

Scaffolding has a shelf life

3. Move up one level of abstraction. The progression they describe runs from local sessions to hosted containers to cloud routines (for example a daily job that buckets incoming feedback and fixes the ones it is confident about) to a Slack-native agent where you see only the messages the agent chooses to send, with the full transcript one link away. Human code review shifts with it, from nitpicks that signal "I read this" to the bigger picture the model may lack, such as why a service boundary sits where it does. Verification, code review, and feedback are named as the three primitives that make this work.

Working one level above the session
What's new vs familiar: map-reduce, adversarial verification and scheduled routines are familiar patterns. The distinctive claim is operational: assume your own scaffolding has a short shelf life and design for removing it. Preconditions: a verification step Claude can run itself (tests, screenshots, recordings), and an environment where it can build and test the project end to end without you.

What you could do with it

Both options stay general because they depend on which of your skills are old enough to carry compensating steps.

New skill

Fan out, adversarially verify, coalesce

A reusable procedure for any "find everything that might be wrong or relevant" task: split into N parallel candidate-finders, run each candidate past several differently framed skeptic passes, and return only what survives with the evidence. The video's examples are code review and trip research, so the trigger could be review, audit or research requests.

Implementation plan

Audit existing skills for expired scaffolding

For each skill you maintain, list the steps that exist to compensate for a model weakness (forced checklists, repeated reminders, hand-holding), then run the skill with and without them on a recent model and keep only the steps that still change the result. This is the to-do-list lesson applied to your own setup. It needs a few representative test inputs per skill.

Ready-to-use prompt

Paste into a fresh Claude conversation or Claude Code. It does not assume you watched the video.

Prompt
You are helping me prune and strengthen my Claude skills. Background: a team that builds Claude Code observed that much of what they build into a harness (checklists, special tools, hand-holding steps) exists to cover a specific weakness of the current model, and that these features often become unnecessary within about a year as models improve. They also found that for "find everything that might be wrong" tasks, the reliable pattern is to fan out many parallel searches, run each candidate through adversarial review from several perspectives, and return only the ones that survive.

Do this with me:
1. List the skills in my skills folder with a one-line purpose each, and ask me to pick one or two I use most.
2. For each chosen skill, read its instructions and mark every step or rule that looks like compensation for a model weakness (for example, steps that force the model to keep going, restate its plan, or double-check basic work). Show me the list and ask which ones I want to test.
3. Propose 3 realistic test inputs per skill, run the skill as written and again with the marked steps removed, and compare the outputs side by side. Tell me which steps changed the result and which didn't, and recommend what to cut. Don't edit anything until I approve.
4. Separately, ask whether any of my skills does a "find all the issues" job (review, audit, research). If so, propose a fan-out version: parallel finders, then 2-3 skeptic passes per candidate with different framings, then a short ranked list with evidence.

Keep every change small and reversible, and use version control so I can undo it.
